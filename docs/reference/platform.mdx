title: "Platform Resources"
description: "Agent-ready commands for worker platform resources."
---

Tovuk platform resources are managed through the CLI and API so agents do not
need dashboard access.

## Commands

```sh
npx tovuk platform --service service_1 --json
npx tovuk database create --service service_1 DB --json
npx tovuk database query --service service_1 DB "select 1" --json
npx tovuk database delete --service service_1 DB --json
npx tovuk kv create --service service_1 CACHE --json
npx tovuk kv put --service service_1 CACHE user:1 '{"name":"Ada"}' --metadata '{"kind":"profile"}' --ttl 3600 --json
npx tovuk kv get --service service_1 CACHE user:1 --json
npx tovuk kv keys --service service_1 CACHE --json
npx tovuk kv namespace delete --service service_1 CACHE --json
npx tovuk queue create --service service_1 jobs --max-retries 3 --retention-seconds 86400 --json
npx tovuk queue delete --service service_1 jobs --json
npx tovuk cron create --service service_1 nightly "0 0 * * *" --json
npx tovuk cron delete --service service_1 nightly --json
npx tovuk durable-object create --service service_1 Room --json
npx tovuk durable-object delete --service service_1 Room --json
npx tovuk binding create --service service_1 AUTH_SERVICE --target auth-service --json
npx tovuk binding delete --service service_1 AUTH_SERVICE --json
npx tovuk limit set worker_requests --period day --value 100000 --json
npx tovuk limit set durable_object_requests --period month --value 1000000 --json
npx tovuk limit set durable_object_sqlite_rows_written --period month --value 50000000 --json
npx tovuk limit delete worker_requests --period day --json
```

## Resource model

- SQLite: service data with row and storage meters.
- SQLite query: migrations, smoke tests, and data inspection with metering.
- KV: small config, sessions, feature flags, and cache metadata.
- Queues: background jobs, retries, emails, and webhook processing.
- Cron triggers: scheduled cleanup, polling, and reports.
- Durable Objects: keyed stateful Rust actors for realtime coordination.
- Service bindings: private worker-to-worker calls without public URLs.
- Usage caps: hard stops and notification thresholds for predictable spend.
- Object storage: service files and media with Class A and Class B operation
  meters.

Delete commands return the refreshed platform resource payload so agents can
verify cleanup immediately and continue without dashboard checks.

KV keys follow Cloudflare's 512 byte limit and may include path separators when
the CLI or API client URL-encodes them. Use object storage for values larger
than 25 MiB.

Use object storage commands for service files and media:

```sh
npx tovuk storage list --service service_1 --json
npx tovuk storage upload --service service_1 ./logo.png uploads/logo.png --public --json
npx tovuk storage download --service service_1 uploads/logo.png ./logo.png --json
npx tovuk storage delete --service service_1 uploads/logo.png --json
npx tovuk limit set object_storage_class_a_operations --period month --value 1000000 --json
npx tovuk limit set object_storage_class_b_operations --period month --value 10000000 --json
```

Queue messages are capped at 128 KB total. Tovuk reserves 100 bytes for
Cloudflare-compatible metadata, so the maximum user body is 127900 bytes. Store
larger payloads in object storage and send the storage path in the queue
message. Queue specs follow Cloudflare limits for 100 message consumer batches,
100 message send batches, 256 KB send-batch payloads, 60 second batch waits,
5000 messages per second per queue, 25 GB backlogs, 250 concurrent consumers,
12 hour visibility timeouts, 24 hour send delays, and 15 minute consumer wall
time.

Agents can tune queue delivery without a dashboard:

```bash
npx tovuk queue create --service service_1 failed_jobs --json
npx tovuk queue create --service service_1 jobs --max-batch-size 10 --max-batch-timeout-seconds 5 --dead-letter-queue failed_jobs --json
npx tovuk queue update --service service_1 jobs --max-batch-size 25 --max-batch-timeout-seconds 10 --json
npx tovuk queue update --service service_1 jobs --clear-dead-letter-queue --json
```

Durable Object usage is metered with Cloudflare-style counters:
`durable_object_requests`, `durable_object_duration_gb_seconds`,
`durable_object_sqlite_rows_read`, `durable_object_sqlite_rows_written`, and
`durable_object_sqlite_storage_bytes`.

## Worker delivery

Agents create resources through CLI/API commands. Deployed Rust workers receive
runtime events through internal HTTP endpoints:

- `POST /.tovuk/queues/<queue>` receives a JSON batch with base64 message bodies.
- `POST /.tovuk/cron/<trigger>` receives `{ "name": "...", "cronExpression": "..." }`.
- Tovuk records worker request, worker CPU, and queue operation meters for
  delivered events.
- Tovuk wakes cold workers before delivery, retries failed queue batches, and
  expires messages at the queue retention limit. Messages that exhaust retries
  move to the configured dead-letter queue when one is set.

Use these endpoints only inside deployed workers. Browser frontends should call
the same-origin Rust API under `/api/*`. Public traffic to `/.tovuk/*` is
blocked by the router.
