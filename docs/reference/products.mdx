Tovuk exposes the product catalog through the CLI and API so agents can make
deployment decisions without dashboard access:

```sh
tovuk pricing --json
tovuk deploy --dry-run --json
```

Use `products[].features`, `products[].best_for`, `products[].avoid_for`,
`products[].meters`, `products[].meter_details`, `products[].pricing_fields`,
and `products[].limit_fields` to choose the smallest resource that fits the
job.
Use `plans[].limits` and `plans[].pricing` before load tests, media uploads,
or paid usage.
`features` is the concrete checklist of supported behavior agents can rely on
before they design or deploy a service.
`meter_details` explains each meter's unit, count semantics, and
`cap_commands` so agents can estimate work and set hard caps before running it.
`limit_fields` includes the relevant runtime, storage, payload, batching,
retention, and monthly allowance fields for each product.
`pricing_fields` includes the exact JSON paths agents should read under each
plan's `pricing` object for included usage and overage costs.
Use `tovuk usage --json` for the authenticated `billingEstimate` line items
before high-throughput work. Every public meter must appear there as either a
priced line item or an explicit zero-price line item.

## Product selection workflow

<Steps>
  <Step title="Read the product catalog">
    ```sh
    tovuk pricing --json
    ```

    Start with `products[]`, not guesswork. Use each product's `features`,
    `best_for`, `avoid_for`, `meters`, `meter_details`, `pricing_fields`, and
    `limit_fields` before changing code.
  </Step>

  <Step title="Dry-run the current project">
    ```sh
    tovuk deploy --dry-run --json
    ```

    Compare the catalog with the project's enabled capabilities, `meters`,
    `meterPlan`, limits, warnings, and `billingEstimate`.
  </Step>

  <Step title="Choose the smallest fit">
    Prefer the product whose `features` match the job and whose `avoid_for`
    list does not describe the workload. Use `limit_fields` and
    `pricing_fields` to confirm the relevant plan limits and overage fields.
  </Step>

  <Step title="Check usage before load">
    ```sh
    tovuk usage --json
    ```

    Review `billingEstimate.lineItems`, then set hard caps for the meters you
    expect to exercise before load tests, media imports, or paid traffic.
  </Step>
</Steps>

## Product Guide

Worker:
Use for Rust public APIs, webhooks, auth callbacks, forms, queue handlers, and
cron handlers. Avoid browser rendering, static files, large media storage, and
single-key serialized state. Features include Rust-only HTTP routes under
`/api/*`, WebSocket upgrades, cron and queue event delivery, private service
bindings, and request, CPU, and response transfer metering. Main meters:
`worker_requests`, `worker_cpu_ms`, and `worker_transfer_bytes`.

Static Frontend:
Use for React, TanStack, Vite, Astro, Svelte, or plain HTML output served at
`/`. Avoid JS or TS servers, SSR handlers, API routes, middleware, and secrets.
Features include static asset serving, same-origin `/api/*` proxying to the
Rust worker, `_headers`, `_redirects`, and frontend-only JavaScript or
TypeScript source. Main meter: `static_transfer_bytes`.

SQLite:
Use for service-local relational data, transactions, migrations, and data
inspection. Create backups before destructive migrations. Avoid files, media,
single-key counters, and cross-service shared storage. Features include
service-scoped bindings, transactional execution, row and storage metering,
manual backups, restore, and storage guardrails. Main meters:
`sqlite_rows_read`, `sqlite_rows_written`, and `sqlite_storage_bytes`.

Object Storage:
Use for user uploads, images, videos, documents, generated files, and downloads.
Avoid relational data, secrets, and high-frequency tiny writes to one key. Main
meters: `object_storage_bytes`, `object_storage_class_a_operations`, and
`object_storage_class_b_operations`, and `object_storage_egress_bytes`.
Agent-readable limits include object size, part count, metadata size, custom
domains per storage bucket, bucket management operations, egress allowance, and
same-key write throughput. Objects can be up to `5 TB`; single-part uploads and
multipart parts can be up to `5 GB`. `tovuk storage upload` automatically
switches to multipart transfer for files larger than 100 MiB. Features include
service-scoped list, upload, download, delete, multipart planning, Class A,
Class B, and egress metering, and private origin storage behind Tovuk API and
media URLs.
Pricing fields include
`pricing.objectStorage.classAOverageUsdMicrosPerMillion`,
`pricing.objectStorage.classBOverageUsdMicrosPerMillion`, and
`pricing.objectStorage.egressOverageUsdMicrosPerTb`.

State:
Use for keyed realtime coordination, rooms, locks, counters, sessions, and
per-tenant state. Use State alarms for per-object scheduled wake-ups and retrying
object-specific work. Avoid general relational data, large files, and stateless
HTTP handlers. Features include State classes, keyed object instances,
serialized key/value operations, one scheduled alarm per object, realtime
coordination behind a Rust worker, and request, duration, row, and storage
metering. Main meters: `state_requests`, `state_duration_gb_milliseconds`,
`state_sqlite_rows_read`, `state_sqlite_rows_written`, and
`state_sqlite_storage_bytes`. Agent-readable limits include class count,
request and duration allowances, storage, payload, WebSocket message size,
soft per-object throughput, CPU, and alarm wall-time.

KV:
Use for small config, sessions, feature flags, cache metadata, and rate-limit
metadata. Avoid SQL queries, large file storage, and strongly serialized
coordination. Main meters: `kv_reads`, `kv_writes`, `kv_deletes`, `kv_lists`,
and `kv_storage_bytes`.

Queues:
Use for background jobs, webhook retries, email tasks, batching, and dead-letter
recovery. Avoid synchronous reads, large payloads without object storage, and
strict global ordering. Main meter: `queue_operations`.

Cron:
Use for UTC scheduled cleanup, polling, reports, and sync tasks. Avoid
long-running workflows without checkpoints and user-facing request handling.
Main meters: `worker_requests` and `worker_cpu_ms`.

Service Bindings:
Use for private worker-to-worker calls between account-owned Rust Worker
services. Avoid browser calls, cross-account public APIs, and retryable
background work that belongs in Queues. Main meters: `worker_requests` and
`worker_cpu_ms` on the called workers.

Secrets:
Use for server-only environment variables, API keys, and build-time
configuration that must not be committed. Avoid frontend public variables,
large files, and secrets that should be encrypted before leaving the user
system. Secrets have no direct usage meter; agents should use the worker and
build environment limit fields.

Custom Domains:
Use for production hostnames on public services with agent-verifiable DNS setup.
Avoid pointing A records at origin hosts, using Tovuk-owned hostnames, or using
domains for private service-to-service calls. Custom domains have no direct
usage meter; agents should use the `customDomains` limit field.

Logs:
Use for build, deploy, and runtime diagnosis in agent repair loops and support
tickets. Avoid long-term analytics storage, secrets, and full user payload
dumps. Main meter: `log_events`.

Builds:
Use for pre-deploy quality gates, release builds, frontend builds, and deploy
promotion. Avoid runtime request handling, background jobs, and artifact storage
after deploy. Main meter: `build_minutes`. Agent-readable limits include build
CPU in millicores, memory, disk, duration, concurrency, environment variable
count, and environment variable size, plus deploy hook rates per service and per
account.

Usage Caps:
Use for load tests, launch guardrails, and paid-usage hard stops. Avoid using
caps as a replacement for code-level rate limits or as a way to hide inefficient
code. Main meters: any supported meter from `tovuk pricing --json`.

## Agent Rules

- Prefer one same-origin full-stack service when a project has both frontend
  and backend needs: static files at `/`, Rust API under `/api/*`.
- Keep JavaScript and TypeScript frontend-only. Move API routes, SSR handlers,
  middleware, and server logic to the Rust Worker.
- Store large payloads in object storage, then pass object paths through Queues
  or SQLite.
- Use State only when one object key needs serialized coordination.
- Use KV for small lookup data where eventual consistency is acceptable.
- Use service bindings for private worker-to-worker calls instead of exposing
  internal APIs publicly. Keep call chains under 32 worker invocations per
  top-level request.
- Use `tovuk env set` for server-only secrets and never commit `.env` files.
- Use `tovuk domains add` and the returned DNS record for custom domains.
- Use `tovuk logs --json` for repair loops and support-ticket evidence.
- Set hard usage caps before high-throughput work:

```sh
tovuk limits set worker_requests --period month --value 10000000 --notify-at-percent 80 --json
tovuk limits set worker_cpu_ms --period month --value 30000000 --notify-at-percent 80 --json
tovuk limits set sqlite_rows_read --period month --value 25000000000 --notify-at-percent 80 --json
tovuk limits set queue_operations --period month --value 1000000 --notify-at-percent 80 --json
tovuk limits set object_storage_class_a_operations --period month --value 1000000 --notify-at-percent 80 --json
tovuk limits set object_storage_egress_bytes --period month --value 1000000000000 --notify-at-percent 80 --json
```

The live `tovuk pricing --json` response is the source of truth for current
free limits, Pro included usage, overage prices, features, meters, meter
details, pricing fields, and limit fields.
The live `tovuk usage --json` response is the source of truth for current
meter usage and `billingEstimate` cost lines. Transfer meters are explicitly
free line items with `free_transfer` billing units, null prices, and zero
estimated cost.
