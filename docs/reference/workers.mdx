title: "Workers"
description: "How Tovuk combines Rust workers with static frontends."

Tovuk worker-static services use one deployable project:

- Rust worker: APIs, auth callbacks, writes, webhooks, and server-side rules.
- Static frontend: TanStack, Vite, Astro, Svelte, plain HTML, or another build
  that emits files.
- One URL: frontend files at `/`, Rust worker requests under `/api/*`.

## One command

Put one `tovuk.toml` in the repo root:

```txt
tovuk.toml
api/Cargo.toml
web/package.json
```

Deploy from the repo root:

```sh
tovuk deploy --wait --json
```

Tovuk builds the worker and frontend together, then returns one `*.tovuk.app`
URL.

```toml
name = "hello-service"
kind = "worker_static"

[worker]
root = "api"
check = "cargo fmt --all --check && cargo check --locked --release --all-targets --all-features && cargo test --locked --release --all-targets --all-features && cargo clippy --locked --release --all-targets --all-features -- -D warnings -D clippy::all -D clippy::pedantic -D clippy::dbg_macro -D clippy::todo -D clippy::unimplemented -D clippy::panic -D clippy::unwrap_used -D clippy::expect_used -D clippy::large_futures -D clippy::large_include_file -D clippy::large_stack_frames -D clippy::mem_forget -D clippy::rc_buffer -D clippy::rc_mutex -D clippy::redundant_clone -D clippy::clone_on_ref_ptr"
build = "cargo build --release"
command = "./target/release/api"
port = 3000
health = "/api/healthz"

[frontend]
root = "web"
check = "bun ci && bun run typecheck && bun run lint"
build = "bun run build"
output = "dist"
```

## Routing

The runtime serves frontend assets first. Requests to `/api` and `/api/*` proxy
to the Rust worker without changing the hostname.

Static frontend output supports Tovuk `_headers` and `_redirects`
files in the build output root. Redirects run before headers, rule files are
not served as assets, `200` rewrite rules can render another same-site asset,
and `301`, `302`, `303`, `307`, and `308` rules return a `Location` response.

Frontend JavaScript and TypeScript are browser and build inputs only. Tovuk
rejects Next API routes, Astro server endpoints, Svelte server handlers,
middleware, SSR handlers, and runtime commands that start Node, Bun, Deno, or
TypeScript servers.

Use CLI resource commands for platform features:

```sh
tovuk database create --service service_1 DB --json
tovuk database query --service service_1 DB "select 1" --json
tovuk kv create --service service_1 CACHE --json
tovuk queue create --service service_1 jobs --json
tovuk cron create --service service_1 nightly "0 0 * * *" --json
tovuk state create --service service_1 Room --json
tovuk state put --service service_1 Room room-1 counter 1 --json
tovuk state get --service service_1 Room room-1 counter --json
tovuk binding create --service service_1 AUTH_SERVICE --target auth-service --json
tovuk binding delete --service service_1 AUTH_SERVICE --json
```

At runtime, workers receive `TOVUK_SERVICE_ID`, `TOVUK_SERVICE_SLUG`,
`TOVUK_SERVICE_PLAN`, `TOVUK_API_BASE_URL`, `TOVUK_RUNTIME_TOKEN`,
`TOVUK_BINDINGS_VERSION`, and one `TOVUK_<RESOURCE>_<NAME>` variable per
SQLite, KV, Queue, Cron, State, and private service binding. Agents should use
those variables to discover the resources they created through the CLI/API.

Use `TOVUK_RUNTIME_TOKEN` only from Rust worker code. The token is scoped to the
current `TOVUK_SERVICE_ID`, so worker code can query its own SQLite database,
read and write KV, send queue messages, update State values, and manage object
storage files without a dashboard or user token.

## Runtime events

Queues and cron triggers are delivered to the same Rust worker process. Tovuk
wakes a sleeping worker before delivery.

- Queue batches are sent as `POST /.tovuk/queues/<queue>`.
- Queue batch size and batch timeout are configured per queue through
  `tovuk queue create` or `tovuk queue update`.
- Cron triggers are sent as `POST /.tovuk/cron/<trigger>`.
- WebSocket upgrades on worker routes are proxied to the Rust worker. Tovuk
  meters the initial worker request, handshake CPU, and response-side tunnel
  bytes under `worker_transfer_bytes`, not idle connection time.

Queue payloads use JSON with base64 bodies:

```json
{
  "queue": "jobs",
  "messages": [
    {
      "id": "message_1",
      "attempts": 1,
      "body": "eyJ0YXNrIjoic3luYyJ9",
      "encoding": "base64"
    }
  ]
}
```

Return any `2xx` status to mark a queue batch complete. Return a non-`2xx`
status or close the connection to retry until the queue retry limit is reached.
When a dead-letter queue is configured, messages that exhaust retries are
copied there for later inspection or replay.
