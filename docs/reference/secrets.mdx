Secrets are encrypted environment values for build steps and Rust Workers.
They are never served to static frontends and must never be committed.

## Secret management workflow

<Steps>
  <Step title="Confirm account and service context">
    Secret changes are account-authenticated and Service-scoped. Confirm account
    setup, then inspect the target Service before listing, setting, or deleting
    names.

    ```sh
    tovuk account show --json
    tovuk service show service_1 --json
    ```

    Check the Service `capabilities`, existing secret names, and `next_actions`
    before asking a human for sensitive values.
  </Step>

  <Step title="Find the missing env name">
    Check logs, `tovuk.toml`, and the deployed Rust worker for the missing
    uppercase env name before asking a human for a value.
  </Step>

  <Step title="List existing secret metadata">
    ```sh
    tovuk env list --service service_1 --json
    ```

    List responses show names and timestamps only. They never return plain
    secret values.
  </Step>

  <Step title="Ask for the value without logging it">
    Ask the human for a secret only when it is not available from their secure
    local environment. Do not paste real secret values into tickets, logs,
    prompts, or browser-visible code.
  </Step>

  <Step title="Store the secret">
    ```sh
    tovuk env set \
      --service service_1 \
      API_KEY="$API_KEY" \
      --json
    ```

    Load the local shell variable from a password manager or secure prompt
    first. Keep literal secret values out of copied commands, tickets, logs, and
    prompts. Read `redeploy_recommended` in the response before deciding
    whether to redeploy the service.
  </Step>

  <Step title="Verify without printing the value">
    ```sh
    tovuk env list --service service_1 --json
    tovuk deploy --dry-run --json
    ```

    Verify the secret name and deploy readiness without printing the value.
  </Step>

  <Step title="Delete stale or rotated secrets">
    ```sh
    tovuk env delete --service service_1 API_KEY --json
    ```

    Read `redeploy_recommended` after deletion and redeploy when the runtime
    should stop receiving the old value.
  </Step>
</Steps>

## API

- `GET /v1/services/{service_id}/env`
- `PUT /v1/services/{service_id}/env`
- `DELETE /v1/services/{service_id}/env/{name}`

Secret values are write-only. List responses show names and metadata, not
plain secret values.

## Dashboard

The dashboard Secrets view is available at `https://tovuk.com/account/secrets`
or `https://tovuk.com/<handle>/secrets`. It lists secret names, stores
write-only secret values, and deletes secrets through the same API routes and rate limits as the CLI.

## Meters and caps

Secrets have no direct usage meter. Worker and build activity still count
against their normal meters.

## Rules

- Put secrets in Tovuk env vars, not in source control.
- Do not print secrets in logs.
- Do not expose secrets to browser code.
- Rotate secrets after accidental disclosure.
- Use separate keys for development, staging, and production Services.
