Tovuk SQLite databases are Service-owned resources attached to the Rust Worker
runtime.

## Database lifecycle

<Steps>
  <Step title="Confirm account and Service context">
    Confirm account setup and inspect the Service before changing databases.
    Check `sqlite`, existing `sqliteDatabases`, `accountUsage`,
    `billingEstimate`, limits, and next actions.

    ```sh
    tovuk account show --json
    tovuk service show service_1 --json
    ```
  </Step>

  <Step title="Enable SQLite for the Service">
    If `tovuk service show service_1 --json` does not include
    `"sqlite": true`, enable the explicit capability in `tovuk.toml` before
    code or migrations depend on managed SQLite.

    ```toml
    [capabilities]
    sqlite = true
    ```

    Then run a dry run so agents can inspect enabled and disabled capabilities,
    meters, `meterPlan`, limits, `billingEstimate`, and `nextActions` before
    creating databases.

    ```sh
    tovuk deploy --dry-run --json
    ```
  </Step>

  <Step title="Create and verify the database">
    ```sh
    tovuk sqlite create --service service_1 DB --json
    tovuk service show service_1 --json
    ```

    Create databases before a deploy needs them, then verify the service
    resources before traffic depends on the binding.
  </Step>

  <Step title="Run one safe query">
    ```sh
    tovuk sqlite query --service service_1 DB "select 1" --json
    tovuk sqlite query --service service_1 DB "select * from users where id = ?" --params '[1]' --json
    ```

    Use `--params` for user-controlled values so the SQL statement stays
    stable and the parameter array stays JSON-parseable.
  </Step>

  <Step title="Run a transaction batch">
    ```sh
    tovuk sqlite batch --service service_1 DB '[{"sql":"create table users (id integer primary key, name text not null)"},{"sql":"insert into users (id, name) values (?, ?)","params":[1,"Ada"]}]' --json
    ```

    Use `sqlite batch` for migrations, seed data, and imports that need
    multiple statements to succeed or fail together. Pass either a JSON array
    of statement objects or an object with a `statements` array.
  </Step>

  <Step title="Back up before migrations">
    ```sh
    tovuk sqlite backup create --service service_1 DB --json
    tovuk sqlite backup list --service service_1 DB --json
    ```

    Create backups before schema migrations, backfills, imports, or destructive
    writes.
  </Step>

  <Step title="Restore or delete deliberately">
    ```sh
    tovuk sqlite backup restore --service service_1 DB sqlite_backup_1 --json
    tovuk sqlite delete --service service_1 DB --json
    ```

    Restore commands create a pre-restore safety backup first. Delete stale
    databases only after migrations, backups, or exports are complete.
  </Step>
</Steps>

Keep schema migrations in source control. Query responses include `rowsRead`,
`rowsWritten`, `vmSteps`, `fullscanSteps`, and `meta.duration`,
`meta.size_after`, `meta.rows_read`, and `meta.rows_written` fields so agents
can fix slow or expensive queries without dashboard access.

## Dashboard

The dashboard Resources view at `https://tovuk.com/account/resources` can run a
single SQLite statement against an existing service database. It uses
`POST /v1/services/{service_id}/sqlite/{database}/query`, shows returned rows,
and displays `rowsRead`, `rowsWritten`, `vmSteps`, `fullscanSteps`, storage,
duration, and next actions. It can also list SQLite backups, create a manual
SQLite backup, and restore a selected backup through the same API routes as the
CLI. Use the CLI for batch statements and parameter arrays.

The dashboard uses these SQLite backup API routes:

- `GET /v1/services/{service_id}/sqlite/{database}/backups`
- `POST /v1/services/{service_id}/sqlite/{database}/backups`
- `POST /v1/services/{service_id}/sqlite/{database}/backups/{backup}/restore`

Create a backup before schema migrations, backfills, imports, or destructive
writes. Restore commands create a pre-restore safety backup first, replace the
live database, update storage meters, and return both backup ids so agents can
verify or roll back without dashboard access.

Delete stale databases only after migrations, backups, or exports are complete.
The delete command removes the binding and local SQLite file set, then returns
the remaining service resources.

## Migration guidance

Recommended pattern:

<Steps>
  <Step title="Track migration files">
    Keep migrations in a tracked `migrations/` directory.
  </Step>

  <Step title="Lock the database">
    Acquire one migration lock per service database.
  </Step>

  <Step title="Apply migrations before traffic">
    Apply pending migrations before serving traffic.
  </Step>

  <Step title="Keep handlers out of migrations">
    Keep request handlers free of schema changes and long backfills.
  </Step>

  <Step title="Back up destructive changes">
    Create a backup before migrations that drop columns, rewrite tables, or
    backfill large data.
  </Step>

  <Step title="Bind SQL parameters">
    Use parameterized SQL with `--params` instead of interpolating user input.
  </Step>
</Steps>

Agents should reject database code that:

- opens unbounded connections;
- runs schema changes on every request;
- stores secrets in source;
- ignores migration errors;
- performs long backfills during request handling.
- concatenates user input into SQL instead of using parameters.

## Limits

Free plans follow Tovuk SQLite limits: 10 service databases, 5 GB total
storage, 500 MB per database, 5 million rows read per day, and 100 thousand
rows written per day.

Pro plans have a 1 TB account hard cap, 10 GB per database, and monthly
included row meters before paid overage pricing. Inspect the exact current
limits and prices with:

SQLite query limits are exposed in `tovuk pricing --json`: 30 second query
timeouts, 50 queries per Worker invocation on Free, 1000 on Pro, 100 bound
parameters, 100 KB SQL statements, 100 columns, and 2 MB row/blob/string values.
Storage is also tracked through the `sqlite_storage_bytes` gauge meter for
account caps and agent-readable usage APIs.

SQLite backup restore windows are exposed as `sqliteTimeTravelDays` in
`tovuk pricing --json`: Free keeps 7 days, Pro keeps 30 days. Restores are
rate-limited per database during each 10 minute window and return
`previousBackup` for safety.

```sh
tovuk usage --json
tovuk pricing --json
```
