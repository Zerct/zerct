---
title: "SQLite"
description: "D1-style SQLite databases for Rust workers."
---

Tovuk service databases are SQLite databases owned by a service and attached to Rust
workers as explicit resources.

```sh
tovuk database create --service service_1 DB --json
tovuk database query --service service_1 DB "select 1" --json
tovuk database query --service service_1 DB "select * from users where id = ?" --params '[1]' --json
tovuk database delete --service service_1 DB --json
tovuk platform --service service_1 --json
```

Agents should create databases before a deploy needs them, then keep schema
migrations in source control. Query responses include `rowsRead`,
`rowsWritten`, `vmSteps`, `fullscanSteps`, and storage usage so agents can fix
slow or expensive queries without dashboard access.

Delete stale databases only after migrations or exports are complete. The
delete command removes the binding and local SQLite file set, then returns the
remaining platform resources.

## Migration guidance

Recommended pattern:

1. Keep migrations in a tracked `migrations/` directory.
2. Acquire one migration lock per service database.
3. Apply pending migrations before serving traffic.
4. Keep request handlers free of schema changes and long backfills.
5. Use parameterized SQL with `--params` instead of interpolating user input.

Agents should reject database code that:

- opens unbounded connections;
- runs schema changes on every request;
- stores secrets in source;
- ignores migration errors;
- performs long backfills during request handling.
- concatenates user input into SQL instead of using parameters.

## Limits

Free plans follow Cloudflare-style SQLite limits: 10 service databases, 5 GiB total
storage, 500 MiB per database, 5 million rows read per day, and 100 thousand
rows written per day.

Pro plans have a 1 TiB account hard cap, 10 GiB per database, and monthly
included row meters before paid overage pricing. Inspect the exact current

D1-style query limits are exposed in `tovuk pricing --json`: 30 second query
timeouts, 50 queries per Worker invocation on Free, 1000 on Pro, 100 bound
parameters, 100 KB SQL statements, 100 columns, and 2 MB row/blob/string values.
