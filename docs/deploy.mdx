Tovuk uses a small project contract so humans and agents can deploy without
guessing.

## Deploy flow

<Steps>
  <Step title="Authenticate">
    Login with GitHub or Google before running account-scoped commands.
  </Step>

  <Step title="Check locally">
    ```sh
    tovuk check --json
    ```

    Fix the first failed check or `agent_instruction` before creating a remote build.
  </Step>

  <Step title="Confirm account setup">
    ```sh
    tovuk account show --json
    tovuk account update --handle <handle> --display-name <name> --json
    ```

    Run the update command only when account setup is incomplete.
  </Step>

  <Step title="Preview deploy intent">
    ```sh
    tovuk deploy --dry-run --json
    ```

    Review deploy intent, meters, limits, and billing estimates without creating a build.
  </Step>

  <Step title="Deploy and inspect the service">
    ```sh
    tovuk deploy --wait --json
    tovuk service show <service> --json
    tovuk service status <service> --json
    ```

    Tovuk queues the build, runs checks, verifies the Rust worker health route,
    and exposes the service on a `tovuk.app` deployment hostname. Use the
    returned service id with `tovuk service show <service> --json` to capture
    capabilities, deploy history, builds, logs, `accountUsage`,
    `billingEstimate`, resources, and next actions. Use
    `tovuk service status <service> --json` when agents need only the compact
    live-state check.
  </Step>

  <Step title="Inspect or cancel deploys">
    ```sh
    tovuk deploy list --json
    tovuk deploy show <deploy_id> --json
    tovuk deploy cancel <deploy_id> --json
    ```

    Cancel stale queued work only when a newer deploy supersedes it.
  </Step>

  <Step title="Use one root for full-stack repos">
    Run `tovuk deploy` from the repo root. The CLI reads the root `tovuk.toml`, builds the configured worker and frontend roots, serves the frontend at `/`, and routes `/api/*` to the Rust worker.
  </Step>
</Steps>

## Local check

```sh
tovuk check --json
```

For Rust workers, check runs the configured quality gates before any remote
build is queued. For static frontends, check runs the configured frontend
quality command. For full-stack services, check validates both roots.

Deploy archives must contain source files only. Tovuk rejects generated
directories, secret files, and compiled artifacts such as `.exe`, `.so`,
`.dylib`, `.jar`, `.node`, and `.rlib`.

## Runtime contract

Rust workers must listen on:

```sh
0.0.0.0:$PORT
```

Do not hardcode the port. Tovuk injects it at runtime. Static frontends do not
need a runtime process; they call Rust workers for dynamic behavior.

## Service Resources

Use CLI commands to create runtime resources without dashboard work:

```sh
tovuk sqlite create --service service_1 DB --json
tovuk sqlite query --service service_1 DB "select 1" --json
tovuk sqlite batch --service service_1 DB '[{"sql":"create table users (id integer primary key)"},{"sql":"insert into users (id) values (?)","params":[1]}]' --json
tovuk sqlite backup create --service service_1 DB --json
tovuk kv create --service service_1 CACHE --json
tovuk queue create --service service_1 failed_jobs --json
tovuk queue create --service service_1 jobs --max-batch-size 10 --max-batch-timeout-seconds 5 --dead-letter-queue failed_jobs --json
tovuk cron create --service service_1 nightly "0 0 * * *" --json
tovuk state list --service service_1 --json
tovuk state create --service service_1 Room --json
tovuk binding create --service service_1 AUTH_SERVICE --target auth-service --json
tovuk service delete service_1 --json
```

Use `service delete` for smoke-test and throwaway services that should not keep
runtime, storage, queue, State, KV, SQLite, or domain resources.

## Agent-ready errors

CLI and API errors should be machine-readable:

```json
{
  "code": "missing_cargo_lock",
  "message": "Cargo.lock is required for reproducible deploys.",
  "agent_instruction": "Run cargo generate-lockfile, commit Cargo.lock, then retry."
}
```

Agents should always fix the first failed check or first actionable log line,
then rerun check before redeploying. After a failed build, start with:

```sh
tovuk logs --build <build_id> --json
```
