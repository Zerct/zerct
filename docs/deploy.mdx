---
title: "Deploy"
description: "How Tovuk deploys Rust workers and frontends."
---

Tovuk uses a small project contract so humans and agents can deploy without
guessing.

## Flow

1. Login with GitHub or Google.
2. Run `tovuk check --json`.
3. Run `tovuk deploy --dry-run --json` to verify deploy intent, meters, and limits.
4. Run `tovuk deploy --wait --json`.
5. Inspect deploy state with `tovuk deploy list --json` or
   `tovuk deploy show <deploy_id> --json`.
6. Cancel stale queued work with `tovuk deploy cancel <deploy_id> --json` when
   a newer deploy supersedes it.
7. Tovuk queues the build, runs checks, and verifies the health route for Rust
   workers.
8. Tovuk exposes the service on a `tovuk.app` deployment hostname.

For full-stack repos, run `tovuk deploy` from the repo root. The CLI reads
the root `tovuk.toml`, builds the configured worker and frontend roots, serves
the frontend at `/`, and routes `/api/*` to the Rust worker.

## Local check

```sh
tovuk check
```

For Rust workers, check runs the configured quality gates before any remote
build is queued. For static frontends, check runs the configured frontend
quality command. For full-stack services, check validates both roots.

## Runtime contract

Rust workers must listen on:

```sh
0.0.0.0:$PORT
```

Do not hardcode the port. Tovuk injects it at runtime. Static frontends do not
need a runtime process; they call Rust workers for dynamic behavior.

## Service Resources

Use CLI commands to create runtime resources without dashboard work:

```sh
tovuk database create --service service_1 DB --json
tovuk database query --service service_1 DB "select 1" --json
tovuk database backup create --service service_1 DB --json
tovuk kv create --service service_1 CACHE --json
tovuk queue create --service service_1 failed_jobs --json
tovuk queue create --service service_1 jobs --max-batch-size 10 --max-batch-timeout-seconds 5 --dead-letter-queue failed_jobs --json
tovuk cron create --service service_1 nightly "0 0 * * *" --json
tovuk state create --service service_1 Room --json
tovuk binding create --service service_1 AUTH_SERVICE --target auth-service --json
tovuk service delete service_1 --json
```

Use `service delete` for smoke-test and throwaway services that should not keep
runtime, storage, queue, State, KV, SQLite, or domain resources.

## Agent-ready errors

CLI and API errors should be machine-readable:

```json
{
  "code": "missing_cargo_lock",
  "message": "Cargo.lock is required for reproducible deploys.",
  "agent_instruction": "Run cargo generate-lockfile, commit Cargo.lock, then retry."
}
```

Agents should always fix the first failed check or first actionable log line,
then rerun check before redeploying. After a failed build, start with:

```sh
tovuk logs --build <build_id> --json
```
